## Project overview

Next.js frontend for a chess web app. Deploys to Vercel. The NestJS backend is a
separate repo (`../backend`), deployed to EC2, and owns all game state.

Current scope is a hotseat game — two players alternating on one board, driven by
the backend's `/games` endpoints. No auth, no multiplayer, no engines yet.

## Stack

- Next.js (see **Next.js version** above — read the local docs, not remembered
  conventions), TypeScript, React
- **`react-chessboard`** for the board. Not `chessboard.js`.
  - It is **"just a board"**: it renders a position and reports interactions. It
    knows no chess rules, and it is not the source of truth for the position.
  - **It provides no keyboard accessibility.** Drag-and-drop is its default
    interaction. A keyboard-operable move path built on `onSquareClick` /
    `onPieceClick` is our responsibility — see **Accessibility**.

## Server is authoritative

**The backend owns the position. This client renders it.**

- Re-render from the state the server returns, never from a local guess. The board is
  controlled by the server's FEN, so a piece only appears to move once the response
  lands — a rejected move simply leaves the board untouched, and the reason reaches the
  player through the live region.
- `chess.js` may later run client-side for legal-move highlighting and optimistic
  rendering. That is **a UX affordance only** — it never becomes the source of
  truth, and it must never be the thing that decides whether a move happened.

## API integration

- `openapi.json` at the repo root is **fetched from the backend, not hand-edited.**
  `pnpm openapi:sync` pulls it from `${OPENAPI_SOURCE_URL}/api-docs-json`;
  `pnpm openapi:generate` writes `src/lib/api/schema.d.ts`.
- Call the API through `src/lib/api/client.ts`. It throws `ApiError` (carrying
  `status` and the raw `body`) on any non-2xx. Its error handling is structural, so
  new backend error DTOs need no client change — keep it that way.
- **All request and response shapes come from the generated types.** Never
  hand-write an interface describing a backend payload — if a shape is missing,
  the spec is stale, so re-sync rather than writing it out. If it is still missing, inform me about it.
- The generated types file is gitignored and rebuilt on install. `openapi.json`
  itself is committed, so Vercel builds never depend on the backend being up.
- The synced spec reflects **deployed** prod, not backend `main`. After merging a
  backend change, wait for its deploy before syncing.
- Backend runs on `3000`, this app on `3001`. The API base URL is an env var —
  never hardcode a URL.

## State

**TanStack Query owns server data. Zustand owns client data. The split is absolute.**

- Anything the server returned lives in the Query cache. A mutation writes the
  server's own response in via `setQueryData`; a rejection invalidates and refetches.
- Zustand holds only ephemeral UI state — selected square, orientation, announcement
  text. Never mirror server data into the store.
- **Always select from a store; never call the hook bare.** A bare call subscribes to
  every field, so one unrelated write re-renders the whole component. Reading a single
  field inline is fine; two or more go through `useShallow` from `zustand/react/shallow`,
  so the component takes one subscription instead of one per field.
- Component state is still fine for state that never leaves one component.
- Provider is `src/lib/query/provider.tsx`, mounted in the root layout.

## Accessibility

Non-negotiable, and the reason this project exists as a portfolio piece.

- `eslint-plugin-jsx-a11y` runs in lint. Violations are errors, not warnings.
- The board must be operable without a mouse and comprehensible to a screen
  reader. Drag-and-drop alone is not sufficient — moves need a keyboard path.
- Announce state changes (move made, check, game over) via a live region rather
  than visual-only feedback.
- **One live region per independent stream of announcements.** A polite region whose
  text is replaced before it has been read simply never speaks it, so two writers on one
  region silently lose messages.
- **Never suppress an a11y rule to make a build pass.** Fix the markup, or ask. Where a
  shadcn primitive is a generic passthrough and cannot carry the association itself,
  register it under `settings['jsx-a11y']` in `eslint.config.mjs` so the rule checks the
  call sites instead.

## Tooling

- **ESLint is pinned to v9 and must not be upgraded.** `eslint-config-next`
  depends on `eslint-plugin-react`, whose peer range caps at `^9`. Upgrading to
  v10 breaks rule loading. Revisit only when that plugin ships v10 support.
- Prettier owns all formatting; `eslint-config-prettier` disables the overlap.
  **Never add `@stylistic` rules** or otherwise make ESLint format code.
- pnpm, pinned via Corepack.
- **All application code lives in `src/`**, imported via the `@/` alias. Config files,
  `public/`, `.env.*`, and `tests/` stay at the repo root. Note that Next 16 renamed
  `middleware.ts` to `proxy.ts`, and it belongs _inside_ `src/`.

## Testing

- **Vitest** (matching the backend) + React Testing Library, jsdom environment.
- **Tests live in `tests/`, mirroring `src/` — never colocated with the code.**
- **Assert on structure, not on strings.** Check the status code, not the error
  message; wording changes on the backend must not break a frontend test.
- Keep the suite small — cover what matters, not every branch.
- Vitest cannot test async Server Components; those need E2E.
- Write tests alongside each feature, not after or before (no strict TDD).
- Test priorities: move submission and rejection handling, rendering from server
  state, and game-over states. **Do not write snapshot tests for the board.**
- Do not test chess rules. The backend and `chess.js` own those.

## Coding style

**Named constants: an `as const` object plus a derived union type — not `enum`.**
Enums are not type-erasable and are nominally typed, which fights the structural
unions coming from generated API types.

```ts
export const BoardOrientation = { WHITE: 'white', BLACK: 'black' } as const;
export type BoardOrientation = (typeof BoardOrientation)[keyof typeof BoardOrientation];
```

**Comments only where the reasoning is not recoverable from the code** — a library
quirk, an ordering constraint, a deliberate trade-off. If a comment restates the
code, delete it. Default to none.

## Git / commits

- **`main` is production, `dev` is integration.** Branch off `dev` and PR into
  `dev`; a release is a `dev` → `main` PR. Never PR a feature branch into `main`.
- Use conventional branch naming (`feat/`, `fix/`, etc) and Conventional Commits
  (`feat:`, `fix:`, `refactor:`, `test:`, etc.)
- **Separate commits by Conventional Commit type.** Never mix types in one commit;
  split the work so each type gets its own, ordered so every commit stands on its
  own. Ask when a change does not obviously belong to a single type.
- **Do NOT commit automatically.** Leave staging and committing to me — make the
  code changes and let me review the diff.
- Keep commit messages short — a couple of paragraphs at most. The diff carries
  the detail; the message says what changed and flags the non-obvious decision.

## Pull requests

- **Assign every PR to me** (`aizazh1`) on creation — `gh pr create --assignee @me`.
- **PRs are squash-merged into `dev`.** Keep a branch to one coherent slice, so
  the squashed commit reads as a single meaningful change.
- **`dev` → `main` release PRs take a merge commit, never a squash.** A squash
  writes a commit `main` has and `dev` does not, diverging the two permanently.
- Both branches are protected: CI must pass before a PR can merge.
- **Do NOT merge automatically.** Opening the PR is where your work stops unless
  I ask otherwise.

## Decision-making

- If a design decision is ambiguous (module structure, naming, where logic should
  live), ASK before proceeding. Do not silently pick an approach on your own.
- Ask **before** writing the code, not after. A decision surfaced once the
  implementation exists is much more expensive to change.
- If a request rests on a mistaken premise, say so and explain the trade-off
  rather than just implementing it as stated.
